# Career Quest — команда Ctrl AI

`hack-f746c068-ctrl-ai` — командный репозиторий Ctrl AI для кейса Career Quest
хакатона HackAlem AI (трек Halyk Bank). Career Quest помогает сотруднику увидеть
карьерную траекторию и выбрать полезный шаг развития, а HR — понять, какие
компетенции проседают. [Репозиторий команды](https://github.com/BAITC-Hacks/hack-f746c068-ctrl-ai).

**Текущее состояние проекта:** реализованы загрузка и проверка датасета, расчёт
дефицита навыков и готовности к следующему грейду, объяснимый выбор 1–3 активностей,
прогноз результата и сравнение вариантов, а также HTTP API с выполнением
активностей, сохранением прогресса, HR-аналитикой и импортом. Доступ сотрудника
и HR проверяется по локальным демо-токенам.
Стек backend: Python 3.11+, Pydantic 2, FastAPI, SQLite. Frontend уже добавлен и
пока работает отдельно на моковых данных; его подключение к HTTP API и
его интеграция с необязательным GPT-маршрутом ещё не реализованы. GPT-выбор
доступен через backend API при наличии серверного ключа; без него действует
локальный алгоритм. Публичная развёрнутая версия пока не указана.

Источник требований — [техническое задание Career Quest](<HackAlem AI_ Career Quest - платформа геймификации жизненного цикла сотрудника..md>),
раздел «КЕЙС: CAREER QUEST». Стартовый кит организаторов с официальной схемой
данных в проект ещё не добавлен.

## Запуск

Клонируйте репозиторий и создайте окружение из его корня:

```sh
git clone https://github.com/BAITC-Hacks/hack-f746c068-ctrl-ai.git
cd hack-f746c068-ctrl-ai
```

```sh
python -m venv .venv
```

Активация в PowerShell: `.venv\Scripts\Activate.ps1`.
В Linux/macOS: `source .venv/bin/activate`.

```sh
python -m pip install -r backend/requirements-dev.txt
python -m backend validate
python -m backend gaps E001
python -m backend readiness E001
python -m backend recommend E001 --limit 3
python -m unittest discover -s backend/tests -v
```

Запуск HTTP API одной командой после установки зависимостей:

```sh
python -m backend.api
```

Swagger: `http://127.0.0.1:8000/docs`. При первом запуске создаются рабочая
SQLite-база и локальные демо-токены в `backend/runtime/`. Для доступа нажмите
**Authorize** и используйте токен из `backend/runtime/access.json`.
Подробный контракт, роли, импорт и пример проверки — в [docs/API.md](docs/API.md).
Для запуска без тестов достаточно зависимостей из `backend/requirements.txt`.

Инструкция запуска frontend находится в [frontend/README.md](frontend/README.md).
Его моковый контракт отличается от текущего HTTP API; отключение моков само по
себе не подключает настоящий backend — потребуется согласовать поля и авторизацию.

Проверка своего набора и расчёт на нём:

```sh
python -m backend --data-dir path/to/dataset validate
python -m backend --data-dir path/to/dataset gaps E001
python -m backend --data-dir path/to/dataset readiness E001
python -m backend --data-dir path/to/dataset recommend E001 --limit 3
```

Успех возвращает JSON в stdout и exit code 0. Ошибка возвращает JSON в stderr
и exit code 1. Загрузка не возвращает частично валидный набор.

## Устройство текущей версии

`backend/data_loader.py` загружает и проверяет все четыре файла как единый набор.
`backend/models.py` задаёт поля и ограничения, `backend/schemas/` содержит
JSON-схемы, `backend/engine/skill_gap.py` считает разрывы,
`backend/engine/grade_progress.py` — готовность, а
`backend/engine/recommendation.py` выбирает активности. `backend/__main__.py`
предоставляет команды `validate`, `gaps`, `readiness` и `recommend`. Генератор и
тесты находятся в `backend/scripts/` и `backend/tests/`.
`backend/engine/progress.py` применяет завершение активности,
`backend/engine/simulation.py` без записи показывает эффект активности и сравнивает
два варианта по тем же правилам ранжирования,
`backend/engine/hr.py` собирает HR-показатели, `backend/api/` предоставляет HTTP API,
`backend/storage.py` сохраняет рабочий снимок и ключи повторных запросов в SQLite.

Основной сценарий из ТЗ — профиль → рекомендация с объяснением → выполнение
активности → обновлённый прогресс → срез для HR — реализован на уровне API.
Frontend пока использует моки; HTTP-сценарий доступен через Swagger. Алгоритм рекомендаций
детерминированный по умолчанию; отдельный endpoint может выбрать первый шаг через
GPT из допустимых локальных вариантов. CLI считает исходные JSON/CSV, API использует
отдельную SQLite-базу: завершённые через HTTP активности не переписывают демо-файлы.

## Этап 1: данные и импорт

В `backend/data/` находится воспроизводимый демонстрационный набор:

| Файл | Содержание |
| --- | --- |
| `employees.json` | 48 синтетических профилей; роль, грейд, стаж, текущие навыки |
| `skills.json` | 16 навыков, 4 карьерных трека, порядок грейдов и требования |
| `events.json` | 26 активностей, целевые роли, предполагаемый прирост и предел уровня |
| `activity_history.csv` | 235 записей участия с датой и статусом |

Все профили, названия активностей, история, требования и веса созданы командой
для демонстрации. Реальные персональные данные и внешние классификаторы не
использованы. Это не официальный датасет организаторов и не подтверждённая HR-матрица.
При появлении официальной схемы потребуется адаптер к внутреннему контракту.

Контракт версии 1.0 определён в `backend/models.py`; машиночитаемые схемы находятся
в `backend/schemas/`. JSON Schema описывает структуру, а Python-валидатор дополнительно
проверяет уникальность, ссылки и ограничения между файлами. Для CSV схема `history`
описывает записи после разбора; точный заголовок:

```csv
record_id,employee_id,event_id,status,event_date
```

Правила:

- JSON и CSV читаются как UTF-8; BOM допускается. Даты — `YYYY-MM-DD`.
- ID уникальны в пределах сущности. Все ссылки на навыки, роли, сотрудников и события должны существовать.
- Уровни — целые числа 0–5; требования, gain и max_level — 1–5.
- Каталог может ограничить отдельный навык меньшим max_level; импорт проверяет это ограничение.
- Роль задаёт собственный упорядоченный список уникальных грейдов.
- У каждого грейда есть непустые требования и хотя бы один обязательный навык.
- Requirement содержит `level`, `importance` (0 < вес <= 1), `mandatory`.
- Неизвестные поля, повторяющиеся JSON-ключи, неверные статусы и даты отклоняются.
- Статусы истории: `invited`, `enrolled`, `completed`, `skipped`, `declined`.
- Пустая история и пустой каталог событий допустимы; профили и матрица навыков обязательны.

История описывает отдельные участия, поэтому один event_id может повторяться у
сотрудника в разные даты. Архивные события сохраняются для целостности истории.
Текущие навыки — готовый снимок: загрузчик не начисляет повторно gain из истории.
Gain — условный ожидаемый эффект демо, а не доказательство освоения навыка.

Генератор использует фиксированный seed 42 и не обращается к сети:

```sh
python -m backend.scripts.generate_demo_data --output demo-copy
```

При наличии файлов генератор откажется их перезаписывать. Явное обновление
поставляемого набора и схем после изменения моделей:

```sh
python -m backend.scripts.generate_demo_data --force --schemas backend/schemas
```

## Этап 2: Skill Gap Engine

`calculate_skill_gaps(employee, career_track)` — чистая функция.
`get_employee_skill_gaps(dataset, employee_id)` находит профиль и его трек.
На границе приложения используется только полностью проверенный `Dataset`.

Следующий грейд берётся из порядка в треке. Для каждого требования этого грейда:

```text
gap = max(required - current, 0)
normalized_gap = gap / required
weighted_gap = normalized_gap * importance
fulfilled = gap == 0
```

Отсутствующий навык считается уровнем 0 — это явное допущение демонстрационного
контракта, а не вывод о способностях реального сотрудника. В реальной системе
неизмеренный уровень стоит хранить отдельно и запрашивать оценку.

Результат содержит все целевые навыки, включая выполненные и дополнительные
(`mandatory=false`), в стабильном порядке skill_id. Навыки сотрудника вне требований
не включаются и не компенсируют дефицит других навыков. Счётчики различают общее
число навыков с gap и число обязательных навыков с gap. Это не рейтинг активностей.

Для `E001`, Middle Backend Engineer → Senior:

| Навык | Текущий | Требуется | Gap | Вес | Weighted gap |
| --- | ---: | ---: | ---: | ---: | ---: |
| System Design | 2 | 4 | 2 | 1.0 | 0.5 |
| Python | 3 | 4 | 1 | 1.0 | 0.25 |
| Public Speaking | 1 | 2 | 1 | 0.4 | 0.2 |
| Communication | 3 | 3 | 0 | 0.8 | 0 |
| SQL | 4 | 4 | 0 | 1.0 | 0 |
| Testing | 4 | 4 | 0 | 1.0 | 0 |

Public Speaking здесь дополнительный, остальные навыки обязательные.
Всего 6 целевых навыков, 3 выполнены, 3 имеют gap, из них 2 обязательные.
История E001 содержит два пропуска и отказ от public speaking; она не влияет на
gap, но учитывается в рекомендациях.

## Этап 3: рекомендации активностей

`get_recommendations(dataset, employee_id, limit=3)` возвращает до трёх активных
событий для роли сотрудника. Оно использует текущий грейд, требования следующего
грейда, дефицит и важность навыков, а также историю участия. Подходят только
активности, которые действительно сокращают хотя бы один разрыв с учётом `gain`
и `max_level`. Расчёт прогнозирует эффект, но пока не изменяет профиль.

Для каждого затронутого навыка вклад равен
`(сокращение разрыва / требуемый уровень) × importance × коэффициент обязательности`.
Коэффициент обязательности равен 1.5 для `mandatory=true` и 1 для дополнительного
навыка. Вклады суммируются. Множитель истории равен
`clamp(1 + 0.05 × completed − 0.15 × skipped − 0.25 × declined − 0.10 × same_event_completed, 0.25, 1.25)`.
История учитывается по событиям, развивающим те же навыки; повтор уже завершённой
активности получает дополнительное снижение. Итоговая оценка — произведение суммы
вкладов и множителя истории. При равной оценке порядок определяется `event_id`.
Коэффициенты — явная эвристика демо, а не обученная модель или утверждённая HR-политика.

Ответ содержит использованные значения и текстовое объяснение. Для E001 первым
выбирается Architecture Mentoring: System Design 2/4 для перехода Middle → Senior,
после активности прогнозируется 3/4; ранее по навыку было одно завершение.
Public Speaking имеет уровень 1/2, но это дополнительное требование, а история
содержит два пропуска и отказ. Поэтому минимальный навык не определяет выбор.
Статусы без рекомендаций: `top_grade`, `no_skill_gaps`, `no_matching_activity`.

### Необязательный GPT-слой

`POST /employees/{id}/ai/recommendations` (Swagger: `/docs`) может выбрать первый
шаг среди максимум 12 подходящих активностей. В модель передаются только роль,
грейды, ID вариантов, измеренные разрывы, возможные приросты и агрегированные
счётчики участия — без имени, ID сотрудника, дат и отдельных записей истории.
Backend проверяет возвращённый ID и строит фактическое объяснение из своих
расчётов. Модель не изменяет навыки и состояние. Остальные до двух шагов берутся
из локального ранжирования. Вызов использует `store=false` и тайм-аут 7 секунд.

Для включения задайте `OPENAI_API_KEY` в окружении процесса backend (не в
репозитории и не в браузере); при необходимости задайте
`CAREER_QUEST_OPENAI_MODEL`, по умолчанию `gpt-4o-mini`. Ключ лучше задать через
защищённые настройки запуска или менеджер секретов. Не вставляйте действующий
ключ в чат, README или исходники. Каждый вызов может
расходовать лимит организации. При отсутствии ключа или ошибке внешнего API
endpoint автоматически возвращает локальный топ-3 с `source=rules` и причиной
в `fallback_reason`; обычный `GET /recommendations` всегда локальный. Живой
GPT-ответ в текущем frontend пока не показывается — демонстрируйте его через
Swagger. Подробности ответа и прав доступа — в [docs/API.md](docs/API.md).

## Этап 4: готовность к следующему грейду

`calculate_grade_readiness(employee, career_track)` использует результат Skill Gap
Engine. Для каждого навыка целевого грейда рассчитывается доля освоения с пределом
100%:

```text
skill_progress = min(current / required, 1)
readiness_percent = 100 × Σ(skill_progress × importance) / Σ(importance)
```

Общий процент учитывает все требования, включая дополнительные навыки. Отдельный
`mandatory_readiness_percent` рассчитывается той же формулой только по обязательным
навыкам. `meets_mandatory` равен `true`, когда закрыт каждый обязательный навык;
его нельзя определять по округлённому проценту. Оба процента возвращаются без
округления, а интерфейс при необходимости округляет их только для отображения.
Процент не означает автоматического повышения: решение о грейде остаётся за HR.

Для `E001` общий взвешенный результат: `100 × 4.25 / 5.2 ≈ 81.73%`,
обязательная часть: `100 × 4.05 / 4.8 = 84.375%`.
System Design даёт `2/4 = 50%`, Python — `3/4 = 75%`.
Так как оба навыка обязательны и имеют дефицит, `meets_mandatory=false`.
У сотрудника на последнем грейде нет следующей цели: статус `top_grade`,
`readiness_percent=null`, `meets_mandatory=null`.

## Этап 5: выполнение активности и HR-сводка

Общая функция `complete_activity(dataset, employee_id, event_id, record_id, completed_on)`
возвращает новый проверенный `Dataset` и `CompletionResult`: изменения навыков,
готовность и рекомендации до и после. Прирост ограничен формулой
`new = max(old, min(old + gain, max_level))`. В историю добавляется `completed`;
старые завершения не начисляются повторно. Повтор с тем же `record_id` возвращает
`already_completed` без прироста; другой сотрудник или событие с этим ID дают
ошибку. Разные ID могут обозначать повторное прохождение. Грейд автоматически
не повышается.

Для E001 выполнение EV002 меняет System Design `2 → 3`, готовность
`81.73% → 86.54%` и первый рекомендуемый шаг с EV002 на EV006. API преобразует
доменный результат в HTTP-контракт через `backend/api/presenters.py` и сохраняет
его вместе с состоянием в SQLite. Идемпотентность HTTP определяется заголовком
`Idempotency-Key`, а не передаваемым клиентом ID истории.

`get_hr_summary(dataset)` возвращает частые дефициты, срез по ролям, сотрудников
без шага с причиной и признаком необходимости действия, а также участие по
событиям и статусам. Считаются записи истории и уникальные сотрудники.
Средняя готовность исключает сотрудников на последнем грейде. Представление
`get_hr_dashboard(dataset)` в `backend/api/presenters.py` адаптирует эту сводку
к HTTP-контракту. Доступ к нему разрешён только HR.

## Дополнительный блок: прогноз и сравнение вариантов

`simulate_activity(dataset, employee_id, event_id)` рассчитывает гипотетическое
завершение через тот же `complete_activity`, что использует настоящий запрос. Оно
возвращает изменения каждого навыка с `gain` и `max_level`, разрывы и готовность
до/после, а также рекомендации после предполагаемого завершения. Новый снимок
датасета отбрасывается: история и навыки в SQLite не меняются. Прогноз включает
влияние гипотетической записи `completed` на последующие рекомендации; грейд
автоматически не меняется.

`compare_activities` сопоставляет две активные и полезные для следующего грейда
активности одной роли. Используется тот же полный список оценённых кандидатов,
из которого выбираются первые три рекомендации, поэтому сравнить можно и вариант
вне топ-3. Ответ показывает оценку, сокращение взвешенного разрыва, множитель
истории, изменения готовности для каждого варианта и объяснение выбора. При
равенстве оценок действует стабильный порядок `event_id`. Маршруты доступны
только самому сотруднику или HR: `GET /employees/{id}/simulate/{event_id}` и
`GET /employees/{id}/compare?first_event_id=A&second_event_id=B`. Список всех
допустимых альтернатив для выбора даёт `GET /employees/{id}/comparison-options`.

Это отдельный необязательный блок принятия решения, а не автоматическое
начисление навыков. Текущая frontend-демонстрация работает на моковых данных;
настоящая синхронизация всего интерфейса с backend API ещё требуется.

## Проверочные профили

| ID | Сценарий |
| --- | --- |
| E001 | Точные разрывы и выбор с учётом истории |
| E002 | Нет измеренных навыков и истории; все целевые навыки считаются нулевыми |
| E003 | Требования превышены; gap остаётся нулевым, повышения автоматически нет |
| E004 | Последний грейд; `status=top_grade`, `target_grade=null`, `gaps={}` |
| E005 | Единственный gap — Testing; подходящей активности в демо-каталоге нет |

Последний грейд отличается от выполненных требований: он не означает готовность
100%. Неизвестный сотрудник даёт `employee_not_found`; невалидная роль или грейд
отклоняются при импорте. Пустые требования — ошибка данных.

Тесты проверяют импорт и связи, воспроизводимость, ошибки файлов, точные расчёты,
пропущенные и избыточные навыки, изменение процента готовности после роста навыка,
конфликтующие факторы рекомендаций, новый профиль и его историю, ограничения
активности по роли, статусу и `max_level`, отсутствие подходящих шагов, последний
