# Career Quest API

## Запуск и доступ

В Docker-сборке интерфейс и API работают вместе: сайт — `http://localhost:8000`,
Swagger — `http://localhost:8000/api/docs`, OpenAPI — `/api/openapi.json`.
Для всех путей ниже добавляйте префикс `/api`, например `/api/health`.
Команда запуска — `docker compose up --build -d`; токены можно прочитать командой
`docker compose exec web cat /var/data/access.json`. SQLite и токены сохраняются
в постоянном томе `/var/data`. Подробности публикации — в [DEPLOY.md](DEPLOY.md).

Из корня репозитория, в активном Python-окружении:

```sh
python -m pip install -r backend/requirements.txt
python -m backend.api
```

Сервер: `http://127.0.0.1:8000`. Swagger: `http://127.0.0.1:8000/docs`.
Машиночитаемый контракт: `http://127.0.0.1:8000/openapi.json`.

При первом запуске создаются `backend/runtime/state.sqlite3` и
`backend/runtime/access.json`. JSON содержит две локальные демо-учётные записи:
HR и сотрудник, привязанный к первому профилю рабочего датасета (в демо — E001).
У каждой случайный bearer-токен. Файл исключён из Git. Токены не выводятся
в ответах API и сохраняются между запусками. Откройте файл локально, скопируйте
нужный `token` в кнопку **Authorize** в Swagger. В HTTP-клиенте используйте
`Authorization: Bearer <token>`.

HR может читать всех сотрудников, выполнять активности от их имени и импортировать
данные. Сотрудник видит и изменяет только собственный профиль. Переданный клиентом
параметр `role` не меняет права. Список сотрудников и HR-аналитика доступны только HR.
Для нового сотрудника HR может проверить профиль своим токеном; чтобы создать
отдельный вход сотрудника, оператор добавляет учётную запись в локальный access.json
с уникальными `account_id`, `token`, нужным `employee_id` и перезапускает сервер.
Это локальный демо-доступ, без SSO, истечения токенов и самостоятельной регистрации.

Настройки через переменные окружения:

| Переменная | Назначение |
| --- | --- |
| `CAREER_QUEST_DATA_DIR` | Каталог четырёх стартовых JSON/CSV; по умолчанию `backend/data/` |
| `CAREER_QUEST_STATE_PATH` | Файл SQLite с рабочим состоянием |
| `CAREER_QUEST_AUTH_FILE` | Локальный JSON учётных записей |
| `CAREER_QUEST_CORS_ORIGINS` | Разрешённые адреса frontend через запятую, например `http://localhost:3000` |
| `OPENAI_API_KEY` | Необязательный серверный ключ для GPT-выбора шага; без него работает локальный алгоритм |
| `CAREER_QUEST_OPENAI_MODEL` | Модель для GPT-выбора; по умолчанию `gpt-4o-mini` |

По умолчанию CORS для другого сайта не включён. Приложение слушает только localhost.
Для запуска в контейнере или на другом порту можно использовать
`python -m uvicorn backend.api.app:app --host 0.0.0.0 --port 8000`.

## Маршруты

| Метод и путь | Доступ | Ответ |
| --- | --- | --- |
| `GET /health` | Все | `{"status":"ok"}` |
| `GET /auth/me` | Авторизованные | ID аккаунта, роль и привязанный employee_id, без токена |
| `GET /employees` | HR | ID, имя, роль и грейд всех сотрудников |
| `GET /employees/{id}` | Сам сотрудник или HR | Профиль, карьерный трек, история с названиями событий, справочник навыков, gaps, readiness, recommendations |
| `GET /employees/{id}/recommendations?limit=3` | Сам сотрудник или HR | Детерминированные рекомендации с объяснением; limit 1–3 |
| `POST /employees/{id}/ai/recommendations` | Сам сотрудник или HR | Необязательный GPT-выбор первого шага с локальным запасным вариантом |
| `GET /employees/{id}/comparison-options` | Сам сотрудник или HR | Все полезные активности для выбора альтернативы, в порядке оценки |
| `GET /employees/{id}/simulate/{event_id}` | Сам сотрудник или HR | Прогноз изменений навыков, разрывов, готовности и рекомендаций без сохранения |
| `GET /employees/{id}/compare?first_event_id=A&second_event_id=B` | Сам сотрудник или HR | Сравнение оценок и факторов двух полезных активностей |
| `GET /events` | Авторизованные | HR: весь каталог; сотрудник: активные события для своей роли |
| `POST /employees/{id}/activities/{event_id}/complete` | Сам сотрудник или HR | Изменения навыков, readiness до/после, новые gaps и recommendations |
| `GET /hr/dashboard` | HR | Средняя готовность, общие дефициты и дефициты по ролям, сотрудники без шага, участие и статистика событий |
| `POST /dataset/import` | HR | Подтверждение импорта и итоговые количества записей |

Формат ошибок: `{"error":"код","message":"описание"}`. Ошибки валидации также
содержат `issues` с местом и причиной. Основные статусы: 401 — нет верного токена,
403 — недостаточно прав, 404 — неизвестный профиль/событие, 409 — конфликт ID или
ключа повторного запроса, 413 — большой файл, 422 — некорректные входные данные,
503 — хранилище временно недоступно. Проверка прав выполняется до чтения чужого профиля.

HR-ответ содержит `average_readiness_percent` по сотрудникам, у которых есть
следующий грейд, и `role_skill_deficits`. Для каждой пары роль/навык там указаны
`eligible_employees`, `affected_employees` и `average_gap_across_role`.

## Прогноз и сравнение

`GET /employees/E001/simulate/EV002` возвращает `skill_changes` с полями
`before`, `after`, `gain`, `max_level`, `applied_gain`, а также
`readiness_before`, `readiness_after`, `gaps_before`, `gaps_after` и
`recommendations_after`. Это предварительный расчёт через тот же доменный
механизм, что и реальное завершение: гипотетическая запись `completed` влияет
на рекомендации после активности. Запрос ничего не записывает в SQLite и не
отмечает активность выполненной. Для исходного E001 / EV002 готовность меняется
с ~81.73% на ~86.54%, System Design — с 2 на 3. Реальное начисление требует
отдельного `POST .../complete`.

`GET /employees/E001/comparison-options` возвращает все подходящие варианты в
том же формате, что `/recommendations`, но без ограничения первыми тремя.
`GET /employees/E001/compare?first_event_id=EV002&second_event_id=EV003`
сравнивает любые две активности, которые сейчас активны, доступны роли и
сокращают разрыв следующего грейда, в том числе вне топ-3. Поля `first` и
`second` содержат те же компоненты оценки, что рекомендации: `score`,
`grade_gap_benefit`, `skill_impact`, `participation`, `history_multiplier`,
`explanation`. Также возвращаются `readiness_after_first`,
`readiness_after_second`, `preferred_event_id`, `score_delta` и общее
`explanation`. Выбор определяется оценкой сокращения разрыва с учётом истории,
а не только изменением процента готовности; при равенстве решает `event_id`.
Одинаковые ID дают 422 `same_event`, активность без полезного воздействия —
422 `not_relevant`. Прогноз и сравнение требуют тех же прав на профиль, что и
обычные рекомендации.

## Необязательный GPT-выбор

`POST /employees/E001/ai/recommendations` берёт до 12 лучших допустимых
активностей из локального алгоритма и просит модель выбрать один `event_id`.
Модель не может добавлять активности, менять уровни навыков или писать в базу.
Выбранный вариант становится первым из максимум трёх; остальные берутся из
детерминированного ранжирования. Все числовые факторы и объяснение активности
рассчитаны backend, а не сочинены моделью. GPT может выбрать вариант ниже
первого по локальной оценке, поэтому `source=gpt` не означает, что его score
наибольший. `considered_count` — число допустимых вариантов, переданных модели
(не более 12).

Ключ задаётся только переменной окружения `OPENAI_API_KEY` процесса backend,
например в защищённых настройках запуска. Не добавляйте его в Git, JSON,
frontend или Swagger. В запрос к OpenAI передаются роль и грейды, ID вариантов,
числовые разрывы и приросты навыков, агрегированные счётчики истории и оценки.
Имя сотрудника, его ID, даты и отдельные записи истории не отправляются.
У запроса `store=false`; при использовании внешнего API всё равно учитывайте
политику обработки данных организации. Время ожидания — до 7 секунд; endpoint
может быть медленнее обычного локального ответа. Каждый вызов с ключом может
расходовать лимит API.

При отсутствии ключа, сбое провайдера или некорректном ID модельного ответа
возвращаются обычные первые три рекомендации: `source=rules` и
`fallback_reason=not_configured`, `provider_unavailable` или `invalid_response`.
При отсутствии подходящих активностей внешний запрос не делается.
`selected_event_id`, `selection_explanation`, `model` и `considered_count`
позволяют увидеть, какой путь сработал. Обычный `GET /recommendations` остаётся
полностью локальным и не расходует API-вызовы. Проверить GPT endpoint можно
через Swagger или HTTP-клиент. В контейнере его полный путь —
`POST /api/employees/{id}/ai/recommendations`.

## Выполнение активности

Тело запроса не требуется. Обязателен заголовок `Idempotency-Key` со значением UUID,
созданным клиентом для одной попытки завершения. При сетевом повторе используйте тот
же ключ. Повтор возвращает исходный ответ с `Idempotency-Replayed: true`, не изменяя
навыки и историю повторно. Первый ответ содержит `Idempotency-Replayed: false`.
Привязка ключа сохраняется в SQLite и переживает перезапуск. Переиспользовать ключ
для другого сотрудника/события нельзя — будет 409. Область ключа — учётная запись.

Активности в каталоге считаются повторяемыми занятиями: новый UUID означает новое
участие и может начислить прирост снова до предела. Для модели одноразовых курсов
потребуется отдельное правило. Одинаковое участие, отправленное разными аккаунтами
или с разными UUID, эта версия не объединяет автоматически.

Для каждого навыка активности:

```text
after = max(before, min(before + gain, max_level))
gain_applied = after - before
```

Уровень не понижается, если сотрудник уже выше max_level. Навыки вне требований
грейда также обновляются, отсутствующий навык имеет уровень 0. Архивные события
и события для другой роли завершать нельзя. Грейд автоматически не повышается.
Дата новой записи истории — текущая дата UTC на сервере.

Ответ содержит `employee_id`, `event_id`, `record_id`, `skill_changes`,
`readiness_before`, `readiness_after`, `skill_gaps` и `recommendations`.
Доменная функция команды возвращает `applied_gain` и рекомендации до/после;
`backend/api/presenters.py` преобразует их в этот HTTP-контракт без повторного
расчёта прироста. Тот же слой адаптирует `get_hr_summary` к HR-ответу.
Изменения и сохранённый ответ записываются одной транзакцией. Конкурирующие изменения
сериализуются SQLite; ошибка проверки не оставляет частичных изменений.

## Импорт

`POST /dataset/import` принимает multipart/form-data:

- `mode`: `append` (по умолчанию) или `replace`;
- `employees`: файл employees.json;
- `events`: файл events.json;
- `skills`: файл skills.json;
- `activity_history`: файл activity_history.csv.

Имена полей важны; исходные имена загружаемых файлов не используются как пути.
Каждый файл — до 5 MiB, UTF-8, BOM допускается. Формат данных совпадает с
документированным внутренним контрактом. Неизвестная схема стартового кита не
поддерживается автоматически.

В режиме `append` можно добавить новые профили, события и записи истории, включая
историю уже существующего сотрудника. Матрица навыков берётся из рабочего набора;
передавать `skills` в этом режиме нельзя. Существующие ID не перезаписываются:
коллизия отклоняется. Новые профили и история проверяются вместе, поэтому история
может ссылаться на сотрудника из того же импорта. Импортированные текущие навыки —
снимок: история не начисляет gain повторно.

В режиме `replace` обязательны все четыре файла. Они полностью заменяют рабочий
набор после проверки. Старый ключ завершения после замены даст 409 `dataset_replaced`;
новая попытка требует нового UUID. Учётные записи при замене не меняются: если
привязанного профиля больше нет, его запрос вернёт 404.

Весь предложенный набор проверяется до сохранения; при ошибке действующие данные
остаются прежними. Стартовые файлы в `backend/data/` не изменяются. CLI продолжает
работать со стартовыми файлами (или `--data-dir`), HTTP API — с рабочей SQLite-базой.

## Проверочный сценарий

1. Войти в Swagger токеном сотрудника E001 и получить профиль и рекомендации.
2. Первым для исходного демо будет EV002 (Architecture Mentoring); посмотреть его
   прогноз и сравнить с EV003 (Public Speaking Meetup). Проверить, что до
   завершения профиль и история не изменились.
3. Завершить EV002 с новым UUID: System Design `2 → 3`, readiness `81.73% → 86.54%`.
4. Повторить запрос с тем же UUID: ответ тот же, второго прироста нет.
5. Перезапустить сервер и проверить, что навык и история сохранились.
6. Войти токеном HR, открыть dashboard, добавить новый профиль и историю через импорт.
7. Проверить, что токен сотрудника получает 403 на чужой профиль, HR-экран,
   прогноз/сравнение чужих активностей и импорт.

Тесты запускаются с дополнительными тестовыми зависимостями:

```sh
python -m pip install -r backend/requirements-dev.txt
python -m unittest discover -s backend/tests -v
```
